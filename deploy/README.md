# Выкладка на прод

Схема: на сервере bare-репозиторий, хук `post-receive` разворачивает код
в рабочую копию и перезапускает systemd-сервис. С рабочей машины —
одна команда `git push production main`.

```
/srv/pumpparse/
  repo.git/      ← сюда пушим, здесь висит хук
  app/           ← рабочая копия, её ставит uv pip
  venv/          ← окружение сервиса, интерпретатор ставит uv
  data/pump.db   ← база, переживает выкладки
  app.env        ← логин, хэш пароля, ключ подписи сессий (600, не в git)
```

Интерпретатор ставит **uv**, а не пакетный менеджер системы: пакету нужен
Python 3.11+, а в Ubuntu 22.04 системный — 3.10, и в репозитории лежит только
3.11.0~rc1. uv кладёт свою сборку CPython 3.12 в домашний каталог сервиса и
системный python не трогает. Версия задаётся переменной `PYVER` в
`setup-server.sh`, путь к uv — `UV_BIN` там же и в `post-receive`; они должны
совпадать, за этим следит тест.

## Первый раз

На сервере (от root):

```bash
git clone <репозиторий> /tmp/pumpparse && sudo bash /tmp/pumpparse/deploy/setup-server.sh
```

Скрипт ставит uv и CPython 3.12, создаёт пользователя, окружение,
bare-репозиторий с хуком, юнит systemd, правило sudo на перезапуск
и заготовку `app.env`.

Пароль (на рабочей машине, на сервер уходит только хэш):

```bash
pumpparse passwd
```

Вывод вписать в `/srv/pumpparse/app.env`. `PUMPPARSE_SECRET` там уже
сгенерирован при установке — второй раз его менять не нужно, иначе
разлогинятся все сессии.

Remote и первый пуш:

```bash
git remote add production pumpparse@<хост>:/srv/pumpparse/repo.git
git push production main
```

Дальше nginx с TLS по образцу `nginx.conf.example`.

## Каждая следующая выкладка

```bash
git push production main
```

Вывод хука приходит прямо в терминал пуша. Что он делает:

1. отбрасывает всё, кроме `main`;
2. запоминает развёрнутый сейчас коммит;
3. раскладывает новый, ставит пакет (`uv pip install --no-deps`), перезапускает сервис;
4. 15 секунд стучится в `/healthz`;
5. если не ответил — **откатывает** на прошлый коммит и завершается с ошибкой.

То есть неудачный пуш не оставляет сервис лежать, но и не считается успешным:
`git push` вернёт ненулевой код.

## Отладка

```bash
sudo systemctl status pumpparse
sudo journalctl -u pumpparse -f
curl -i localhost:8000/healthz
```

Откатиться руками на конкретный коммит — просто запушить его:

```bash
git push production <sha>:main --force
```

## Авторизация

Включается наличием `PUMPPARSE_PASSWORD_HASH` в окружении. Если переменной
нет, сервис поднимется **без пароля** и напишет об этом в лог при старте —
на проде это всегда ошибка конфигурации.

| Переменная | Смысл |
|---|---|
| `PUMPPARSE_USER` | логин, по умолчанию `admin` |
| `PUMPPARSE_PASSWORD_HASH` | PBKDF2-SHA256, 600k итераций; генерирует `pumpparse passwd` |
| `PUMPPARSE_SECRET` | ключ подписи сессий; смена = разлогинить всех |
| `PUMPPARSE_TRUST_PROXY` | `1` — считать попытки входа по `X-Forwarded-For`. **Только когда перед сервисом реально стоит nginx**, иначе клиент подделывает заголовок и обходит блокировку |
| `PUMPPARSE_SECURE_COOKIE` | `1` — ставить на сессию флаг `Secure`. Нужен за TLS-прокси: адрес привязки об этом не говорит ничего, сервис слушает петлю. Без https с ним не войти |

Обе последние переменные включаются **одновременно с nginx и сертификатом**,
не раньше. До этого момента интерфейс доступен через SSH-туннель:

```bash
ssh -L 8000:127.0.0.1:8000 gta-sp
# и открыть http://127.0.0.1:8000
```

Сессия — подписанная HMAC cookie `pp_session` (HttpOnly, SameSite=Lax, Secure
вне localhost), живёт 14 дней. Хранилища сессий нет, поэтому перезапуск при
выкладке никого не выкидывает. После 5 неудачных попыток вход с этого адреса
блокируется на 5 минут.

Локально, без TLS:

```bash
pumpparse web --lan --insecure-cookie
```

`--insecure-cookie` снимает флаг `Secure`, иначе браузер не отдаст сессию по http.
