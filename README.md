# pumpParse

Сканер новых токенов pump.fun с профилированием создателя. Только stdlib, без зависимостей.

## Источники данных

Публичный API pump.fun, без ключей и авторизации (проверено: работает даже без User-Agent,
Cloudflare-челлендж не выдаётся). Парсить HTML не требуется — фронт берёт данные оттуда же.

| Эндпоинт | Назначение |
|---|---|
| `frontend-api-v3.pump.fun/coins` | лента токенов; фильтры `sort`, `order`, `complete`, `creator`, `includeNsfw` |
| `frontend-api-v3.pump.fun/coins/{mint}` | карточка монеты |
| `frontend-api-v3.pump.fun/users/{address}` | профиль: username, подписчики, x_username |
| `frontend-api-v3.pump.fun/sol-price` | цена SOL |
| `frontend-api-v3.pump.fun/coins/top-holders/{mint}` | топ-50 холдеров с флагами `isDev`, `isSniper`, `isBundler` |
| `swap-api.pump.fun/v2/coins/{mint}/trades` | сделки (v1 отдаёт 410); не больше 100 за страницу, иначе 400 |
| `swap-api.pump.fun/v1/coins/{mint}/candles` | свечи OHLCV |

Мертвы и не используются: `frontend-api.pump.fun` (530), `-v2` (503), `/coins/search`,
`/replies`, `/candlesticks`, `/trades/all`, `/coins/king-of-the-hill` — 404. Страница режется
до 70 записей независимо от `limit`, дальше `offset`.

## Сеть

Только **Solana mainnet-beta** (`chain_id = solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp`).
Серверного фильтра по сети нет — параметры `chain`/`chainId` игнорируются, как и `?user=`,
поэтому отсев идёт на клиенте в `api.is_solana()`: `coins()` режет ленту, `coin()` возвращает
`None` для чужой сети. Счётчик отброшенного — `PumpAPI.skipped_foreign`.

На практике вся выдача и так солановая (проверено на 490 монетах в трёх срезах), а поле
`multichain_family` у всех равно 1 — мультичейн заложен в схеме API, но в данных пока не появился.
Фильтр стоит на будущее, чтобы вторая сеть не протекла в статистику молча.

Внутри Solana различается валюта пары `quote_mint`: нативный SOL, wrapped SOL (в основном
у съехавших монет) и USDC у небольшой доли. Все метрики считаются по `usd_market_cap`,
поэтому на них это не влияет — но при расчётах напрямую через `virtual_sol_reserves`
USDC-пары надо отсеивать отдельно.

## Использование

    python -m pumpparse scan                      # лента новых токенов
    python -m pumpparse scan --min-migrated 1     # только от создателей с миграцией
    python -m pumpparse scan --min-score 50       # только рейтинг >= 50
    python -m pumpparse dev <кошелёк|минт>        # профиль создателя
    python -m pumpparse coin <минт>               # карточка + сводка по сделкам

Всё пишется в SQLite (`pump.db`, таблицы `coins` и `creators`), профили создателей кешируются
на час, чтобы не долбить API на каждом токене конвейерного дева.

## Веб-интерфейс

    python -m pumpparse web                 # http://127.0.0.1:8000
    python -m pumpparse web --port 8080 --interval 30

Локальный сервер на stdlib, без зависимостей и без CDN — работает офлайн.
Слушает только `127.0.0.1`.

Архитектура: фоновый поток тянет свежие монеты и профилирует девов в SQLite,
страница читает уже готовое из БД и потому не ждёт сеть. Опрос можно ставить
на паузу и менять интервал прямо из шапки.

Что на странице:

* конструктор условий — метрика, оператор, значение, окно, период; правила висят чипсами,
  снимаются по клику, режим И/ИЛИ переключается;
* пресеты одной кнопкой;
* таблица: возраст, тикер, капа, соцсети, дев, всего монет, миграций, срез по окну 10
  (`миграции/монеты · подряд · gap`), score с цветовой шкалой, вердикт;
* клик по деву открывает панель со всеми окнами, полной статистикой и ссылками
  на его мигрировавшие монеты.

Вход по паролю выключен, пока не задан `PUMPPARSE_PASSWORD_HASH` — локально
он и не нужен. Как включить, см. «Прод» ниже.

API, если захочется дёргать самому: `GET /api/status`, `GET /api/feed?rules=mig>=3@10;streak>=2@10&any=0`,
`GET /api/dev?address=...`, `POST /api/worker {running, interval}`.

Окна воркер считает заранее — 5, 10, 20, 50, и каждое ещё по периодам
1h, 6h, 24h, 7d, 30d — поэтому в UI доступны только они. Девы, профилированные
до появления нужного среза, правилом не проверяются и показываются отдельным
счётчиком «без данных», а не молча пропадают: следующий проход сканера их
дотянет, либо можно открыть дева вручную.

## Прод

Установка и зависимости:

    pip install --no-deps .        # зависимостей нет, только стандартная библиотека

`requirements.txt` пуст намеренно — сервис не тянет ничего с PyPI, и `--no-deps`
это фиксирует: незаметно появиться новая зависимость не может. Нужен Python >= 3.11.

Выкладка — пушем в сервер:

    git push production main

На сервере bare-репозиторий с хуком `post-receive`: он раскладывает код,
переустанавливает пакет, перезапускает systemd-юнит, проверяет `/healthz`
и **откатывается на прошлый коммит**, если сервис не поднялся.
Разовая настройка сервера — `sudo bash deploy/setup-server.sh`; интерпретатор
там ставит uv, системный python не трогается.

Авторизация — логин и подписанная cookie-сессия, включается переменными окружения:

| Переменная | Смысл |
|---|---|
| `PUMPPARSE_USER` | логин, по умолчанию `admin` |
| `PUMPPARSE_PASSWORD_HASH` | PBKDF2-SHA256; печатает `python -m pumpparse passwd` |
| `PUMPPARSE_SECRET` | ключ подписи сессий; смена разлогинивает всех |

Пароля на сервере нет даже в хэшированном виде до тех пор, пока вы сами его
туда не впишете: `passwd` считает хэш локально и только печатает строки для
файла окружения. Сессия живёт 14 дней и переживает перезапуск при выкладке,
после 5 неудачных попыток вход с адреса блокируется на 5 минут.

Подробности, nginx с TLS и отладка — в [deploy/README.md](deploy/README.md).

## Пул: девы и их новые монеты

Пул — список **девов**, а не монет. Дев попадает туда **автоматически**, когда
его новая монета проходит фильтр. Дальше каждая его следующая монета поднимает
его наверх списка с горящей пометкой «новая монета» — фильтр по капе, возрасту
и правилам к ней уже не применяется: дев уже отобран, интересен сам факт
запуска. Единственное, что проверяется у всех без исключения, — накрутка
(см. ниже): монету, которую крутят ботами, в пул не пустят и от знакомого дева.

Фильтр живёт на сервере: его считает фоновый воркер, поэтому пул наполняется
и при закрытой странице. Настройки хранятся в БД (`settings`, ключ
`pool_config`) и переживают перезапуск.

Каждую новую монету воркер проверяет **один раз** — когда впервые её увидел
и посчитал профиль создателя. Дальше к ней не возвращается.

В строке дева: когда обновлён, сколько его монет в пуле, последняя монета
(тикер, возраст, капа, соцсети), срез по окну из правил, score и «почему
прошла» — снимок причин для последней монеты. Прошлые монеты дева из пула —
строкой ниже, ссылками. Счётчик на вкладке — сколько девов с непрочитанной
монетой; «отметить прочитанными» гасит пометки у всех.

### Параметры

| В интерфейсе | В конфиге | На что влияет |
|---|---|---|
| «отбор включён» | `enabled` | Выключенный фильтр просто ничего не добавляет. Уже собранное остаётся на месте |
| «капа $ от» | `mcap_min` | Нижняя граница `usd_market_cap` **на момент появления**. Монета без капы считается нулевой |
| «капа $ до» | `mcap_max` | Верхняя граница. Пусто или 0 — без ограничения |
| «свежесть» | `age_max_sec` | Максимальный возраст от `created_timestamp`. «без ограничения» = 0. По умолчанию 15 минут |
| «только с соцсетями» | `require_social` | Требует хотя бы одно из X / Telegram / сайта |
| «score от» | `min_score` | Нижняя граница рейтинга создателя (0..100, см. «Метрики создателя») |
| конструктор условий | `rules` | Условия по деву в том же формате, что и в ленте: `mig>=3@10`, `streak>=3@10/24h` |
| «все (И)» / «любое (ИЛИ)» | `any` | Как складывать условия из конструктора |
| «отсеивать монеты, которые крутят» | `wash_filter` | Проверка накрутки по сделкам и холдерам, включена по умолчанию |

Условия по деву — те же, что на вкладке репозитория, но **набор у пула
свой**: фильтр в ленте на пул не влияет и наоборот.

### Порядок проверок

Важен, потому что в столбце «почему прошла» видно только то, что монета
успела пройти до отказа:

0. дев уже в пуле — пункты 1–6 пропускаются, монета сразу идёт на п. 7;
1. капа — `mcap_min`, затем `mcap_max`;
2. возраст — `age_max_sec`;
3. соцсети — `require_social`;
4. наличие профиля дева: не посчитан — монета не берётся;
5. `min_score`;
6. условия из конструктора. Если нужный срез у дева не посчитан, монета
   не берётся: судить не по чему;
7. накрутка — `wash_filter`. Стоит два запроса к API, поэтому идёт последней
   и только для монет, прошедших всё остальное. Если API не ответил, монета
   проходит с пометкой «не проверено» — сбой сети не повод её терять.

Причины пишутся в момент добавления и потом не пересчитываются — это снимок
того, как монета выглядела, когда попала в пул.

### Что стоит держать в голове

**Фильтр не применяется задним числом.** Он влияет только на монеты, которые
воркер увидит *после* сохранения. Правку конфига воркер перечитывает на каждой
монете, а не раз в круг, поэтому новые настройки начинают действовать сразу,
не дожидаясь следующего прохода.

**Капа и возраст меряются в момент обнаружения.** Монета, выросшая в капе
через час, в пул задним числом не попадёт. И наоборот: попавшая по капе
$5 000 останется в пуле, даже если потом сдулась.

**Возраст успевает подрасти.** Воркер профилирует девов по очереди, каждый
профиль — несколько запросов к API. На полной странице обход занимает минуты,
поэтому монеты из хвоста доходят до проверки заметно старше, чем были
в момент опроса. Слишком узкая «свежесть» (до 1 минуты) отсечёт почти всё.

**Очистка пула необратима.** «Очистить пул» удаляет журнал, но монеты уже
помечены как виденные, и воркер к ним не вернётся — девы появятся снова
только со следующей своей монетой, прошедшей фильтр.

**Монета попадает в журнал один раз** — повторное добавление того же минта
игнорируется.

## Накрутка: монеты, которые «крутят»

На pump.fun хватает монет, у которых объём, холдеры и капа нарисованы ботами.
По данным API их видно без ончейна — по сделкам (`trades`) и топ-холдерам
(`top-holders`, где pump.fun сам ставит флаги `isDev` / `isSniper` /
`isBundler`). Срез ~30 монет с активностью (сентябрь 2026) даёт четыре
признака, и по каждому между живыми и накрученными зазор в разы:

| Признак | Что это | Порог | Живые | Накрученные |
|---|---|---|---|---|
| **пыль** | бот-объём: сотни сделок по копейке от разных кошельков | ≥ 50% сделок дешевле $1 при ≥ 20 сделках | 0–25% | ADAMITY 90%, NYT Coin 94%, BBC 95% |
| **самокрутка** | пара адресов гоняет монету туда-сюда | ≥ 10 сделок на кошелёк при ≥ 30 сделках | 1–7 | beer 50 (100 сделок / 2 адреса), SXSN 16, Pink Bull 14 |
| **клоны** | бандл-кошельки с одинаковым балансом (один владелец) | ≥ 5 холдеров с одним балансом, дев не в счёт | 1–4 | NYT Coin 42 из 50, BBC 49 |
| **бандл** | pump.fun пометил холдеров бандлерами | ≥ 5 штук и ≥ половины топа | до 30% | SHI 15 из 26 на запуске |

Вердикт — любой из признаков. Что ещё видно, но критерием не стало:
`boost_mode` (IN_PROGRESS / COMPLETED) стоял у всех монет, накрученных
до миллионов за минуты, но и у пары живых — отдаётся как справка. Показательный
пример: NYT Coin с капой $3.1M через 7 минут после запуска, через 4 минуты —
$94k.

Проверка запускается только для кандидатов в пул (два запроса на монету),
вердикт пишется на монету в БД (`coins.wash`) и виден в ленте и в пуле
пометкой «крутят» у тикера. В CLI — `python -m pumpparse coin <минт>`.
Пороги лежат в `wash.py` константами, рядом — откуда каждое число.

## Правила отбора девов

Основной фильтр — по **окну последних запусков**, а не по всей истории. Формат:

    <метрика><оператор><значение>@<окно>[/<период>]

    python -m pumpparse scan --rule "mig>=3@10"                   # 3 миграции из последних 10
    python -m pumpparse scan --rule "streak>=3@10"                # 3 миграции ПОДРЯД внутри последних 10
    python -m pumpparse scan --rule "streak>=3@10/24h"            # то же, но среди монет за последние сутки
    python -m pumpparse scan --rule "mig>=3@10" --rule "stay<=0.5@10"   # оба условия
    python -m pumpparse scan --rule "mig>=2@5" --rule "mig>=4@20" --any # любое из
    python -m pumpparse dev <кошелёк> --rule "streak>=3@10"        # разбор по условиям, с фактами

Окно режется от самых свежих монет. Если монет меньше окна, считается по тому, что есть.
`streak` смотрит только внутрь окна: серия, начавшаяся раньше него, обрезается его границей.

Период (`/24h`) сужает окно по времени: сначала отбрасываются монеты старше
периода, и уже из оставшихся берутся последние n. Так `streak>=3@10/24h`
находит дева, сделавшего три миграции подряд *сегодня*, и не путает его
с тем, у кого такая серия была полгода назад. Периоды фиксированы — `1h`,
`6h`, `24h`, `7d`, `30d` — потому что воркер считает их заранее, как и окна.
Без периода — вся история, как раньше.

Старые имена `grad` и `dead` в правилах ещё принимаются: `grad` читается как `mig`,
`dead` — как `stay`.

### Метрики

| Метрика | Что значит |
|---|---|
| `mig` | миграций в окне, любая площадка, штук |
| `ray` | из них именно в Raydium (см. ниже — на новых монетах это всегда 0) |
| `pswap` | из них в PumpSwap |
| `streak` | самая длинная серия миграций **подряд** в окне, штук |
| `rate` | доля миграций в окне, 0..1 |
| `stay` | доля оставшихся на кривой в окне, 0..1 |
| `medath` / `bestath` | медианный и лучший ATH в окне, $ |
| `pace` | запусков в сутки внутри окна |
| `gap` | сколько монет запущено после последней миграции (0 — последняя же и уехала) |
| `social` | доля монет с привязанным X/TG/сайтом |
| `coins` | сколько монет реально попало в окно |

Операторы: `>=` `<=` `>` `<` `==`. Несколько `--rule` складываются по И, с `--any` — по ИЛИ.

### Пресеты

| Пресет | Раскрывается в |
|---|---|
| `runner` | `mig>=3@10` — 3 миграции из последних 10 |
| `series` | `streak>=3@10` — 3 миграции подряд внутри последних 10 |
| `hot` | `mig>=2@5` — дев в ударе прямо сейчас |
| `quality` | `rate>=0.3@10` и `coins>=5@10` |
| `fresh` | `mig>=1@5` и `pace<=5@10` — недавняя миграция, не конвейер |
| `whale` | `bestath>=100000@10` |
| `warm` | `gap<=3@20` — миграция была совсем недавно |

    python -m pumpparse scan --preset runner
    python -m pumpparse scan --preset hot --preset whale --any

## Куда мигрируют монеты

Короткий ответ: **в Raydium больше никто не мигрирует**. С весны 2025 pump.fun
уводит ликвидность в собственный AMM **PumpSwap**, и по срезам это видно прямо
в данных API (монеты с `complete=true`, без Mayhem):

| Срез | всего | Raydium | PumpSwap |
|---|---|---|---|
| 2024-01 | 70 | 52 | 18 |
| 2024-03 | 70 | 44 | 24 |
| 2026-08 | 57 | **0** | 57 |
| 2026-09 | 50 | **0** | 50 |

Площадка определяется по полям `raydium_pool` и `pump_swap_pool` — они
взаимоисключающие (проверено на 140 монетах: пересечений 0). Основная метрика `mig` считает **обе площадки** — и Raydium, и PumpSwap; на ней
построены все пресеты, по ней же считаются `streak`, `rate` и `gap`. Метрика `ray`
и поле `migrated_raydium` есть, и правило `ray>=3@10` работает — но на свежей
ленте оно не найдёт никого, и это состояние рынка, а не поломка фильтра.
Для отбора девов по свежим запускам нужен `mig` (любая площадка) или `pswap`.
Редкий случай — кривая закрыта, но API не отдал ни одного пула: такая монета
попадает в `mig`, но ни в `ray`, ни в `pswap` (на 140 монетах — одна).

## Метрики создателя

* `total_coins` / `migrated` — сколько монет запущено и сколько мигрировало;
  `migrated_raydium` / `migrated_pumpswap` — разбивка по площадке.
  «Мигрировала» = `complete` **и пустой `mayhem_state`**: бондинг-кривая закрыта,
  ликвидность ушла в пул.
* Одного `complete` недостаточно. У монет режима **Mayhem** он тоже `true`, хотя
  ликвидности в пуле нет: pump.fun показывает им значок «Completed» при капе в
  пару долларов. Отличает их поле `mayhem_state` (`active`/`paused`/`completed`),
  у обычных монет пустое. На выборке из 350 монет с `complete=true` разделение
  чистое: без `mayhem_state` минимальный ATH — $41k (кривая закрывается около
  $69k), с ним медианный ATH — $4.5k, медианная капа — $2. В истории дева такие
  монеты считаются оставшимися и помечаются значком `mayhem`.
* `migration_rate` — доля миграций; главный сигнал качества дева.
* `stayed_coins` / `stayed_rate` — сколько монет осталось на кривой.
  Монета всегда в одном из двух состояний: **миграция** или **осталась**;
  прежнего «мертва» (старше часа и капа < $5k) больше нет — порог был выдуманным,
  API не даёт признака смерти. Из score ушёл и штраф за мёртвые монеты,
  так что рейтинги стали выше прежних.
* `launches_per_day` — темп; у конвейерных девов десятки в сутки.
* `best_ath` / `median_ath` — пиковая и медианная капитализация запусков.
* `score` 0..100 и `verdict` — сводная оценка.
* `truncated` — история упёрлась в лимит (300 монет), доля миграций занижена.

## Ограничения

* API не отдаёт комментарии, поиск по названию и историю кошелька-покупателя.
* Рейт-лимита на практике не наблюдалось, но клиент держит 4 запроса/с и ретраит 429/5xx.
* Для реалтайма секундной точности HTTP-поллинга мало — нужен WebSocket-фид.
